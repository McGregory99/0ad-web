# T0.4d report — resource query call sites

STATUS: done

Read-only runbook: nothing was built and no source was edited. Scratch copy extracted to
`runs/T0.4d/src/`; the only files written are this report and that directory.

**Headline (observed):** the four hot callbacks are two *pairs* per entity:
`QueryInterface(ent, IID_90)` followed by `GetCurrentAmount`/`GetNumGatherers`, and
`QueryInterface(ent, IID_89)` followed by `GetCarryingStatus`. All of them are reached through four
tiny wrappers in `simulation/ai/common-api/entity.js` (`resourceSupplyAmount`,
`resourceSupplyNumGatherers`, `resourceCarrying`, and `queryInterface` itself), which are called from
**loops over supplies and over the AI's own units** in `petra/worker.js`,
`petra/baseManager.js`, `petra/entityExtend.js`, `petra/attackManager.js`,
`petra/attackPlan.js` and `petra/navalManager.js`.

## Summary (observed/inferred): what one batched query would need to return to replace these calls

**Observed facts to design against:**
1. The three hot values are: `GetCurrentAmount` (amount left), `GetNumGatherers` (gatherers
   assigned), `GetCarryingStatus` (what a unit carries) — the first two on `ResourceSupply`
   entities, the third on `ResourceGatherer` units.
2. Callers always query **one entity at a time inside a loop** over the AI's candidate supplies,
   its own units, or its fishable supplies (`baseManager.js:415`, `worker.js:495`, `worker.js:815`,
   `worker.js:926`, `worker.js:985`, `navalManager.js:64`, `attackPlan.js` loop).
3. The engine's `qicall` re-does `QueryInterface` for every method call, and `qi` returns only a
   boolean, so today each value costs 2 RPC round-trips (JSON encode/decode + worker wake-up).

**Inferred design for one batched query per computation (the shape the data would need):**
- A single `simcall`-style request per AI computation returning a map keyed by entity id, e.g.
  `{ "supplies": { "<entId>": { "amount": <n>, "gatherers": <n>, "max": <n> } },
     "carrying": { "<entId>": [ { "type": "<res>", "amount": <n> } ] } }`.
- It must be produced in **one pass over `GetEntitiesWithInterfaceUnordered(IID_ResourceSupply)` /
  `(IID_ResourceGatherer)`** (`ComponentManager.h:265-266` already exposes those lists), which is
  exactly the iteration the AI is doing itself today — so the engine can do it once instead of the
  AI doing it per entity.
- It should include `maxGatherers` (or `max` from the template) because `isSupplyFull` and
  `worker.js:818` compare `GetNumGatherers()` against `maxGatherers()`; otherwise the batch only
  halves the calls.
- It should be **invalidated per turn** (the AI caches read-only queries for one computation
  already, `READ_ONLY_METHOD` in `ai-worker.js:183-195`), and must not be used across
  `AddModifiers`/state-changing calls.
- The AI's own bookkeeping (`GetTCGatherer`, `GetMetadata`) is not an engine callback, so it can
  stay in JS: only the three engine values need to travel.

**Derived size of the win:** today the four hot keys cost 26.0 s of the 26.3 s total callback time
(24,559 ms of 26,320 ms in T0.4c). Replacing 498,139 method calls + 562,499 interface lookups with
one map per `compute` request (≤ 12,420 requests, of which half currently issue no callbacks at
all) would remove essentially all of that — the remaining per-turn work would be a single
encode/decode of the map.

**Caveat (inferred):** `GetCarryingStatus` is per-unit and only meaningful for units that have a
`ResourceGatherer`; a batched map over *all* gatherer units every turn may be larger than the
handful of units the AI actually inspects, so a hybrid (batch of supplies always; carrying status
only for the AI's own units, which the AI already tracks in JS) may be cheaper than one uniform
batch.
