## Step 3 md5 table and which click worked

The md5 comparison the runbook prescribes (**observed**):

| Shot | md5 |
|---|---|
| `noclick` (`wait:25,resize:1600:900,wait:5,shot:noclick`) | `f8a083272fbcb575223228942082ed56` |
| `sp_scaled` (`click:614:691`) | `39980479cadb90b3ae760f9a7658048a` |
| `sp_unscaled` (`click:491:553`) | `9eba414df061786599d655ab83cb6bf4` |

All three differ, so **the md5 test cannot tell which click opened the submenu**. I verified why, with
pixel diffs (24-bit BMP via `sips`, compared by `runs/T2.1b/bmpdiff.mjs`):

- Two shots taken **0.05 s apart with no input** differ in **47.75 %** of pixels (687,671 of 1,440,000).
- Two runs of the *identical* no-click script (`noclick` vs `n30`) differ in **61.76 %** of pixels.
- Two shots inside one run, 0.2 s apart before any click, differ in **37.02 %**.

**Derived:** the rendered menu changes almost completely between any two captures (animated background
and/or non-deterministic GPU output), so screenshot md5/pixel comparison is useless for this question at
any timescale I tried.

**Observed:** the click dispatch itself works (the 1280x720 control starts a game), so the harness is
fine. **Observed:** neither the 1.25-scaled point nor the unscaled point, at 1600x900, led through the
submenu to a game — with a *fresh* 1600x900 viewport either. **Derived:** the runbook's premise that the
menu button moves to (614,691) at 1600x900 does not hold, so I could **not** determine which click opened
the single-player submenu; both remained unproven.

Why the scaling premise fails (**inferred** from the GUI files extracted from `public.zip`):
`gui/pregame/menupanel.xml` places the menu buttons inside a panel with *fixed pixel* geometry
(`mainMenu size="60 -2 300 100%+2"`, `mainMenuButtons size="8 146 100%-8 346"`) and
`gui/pregame/MainMenuItemHandler.js:37-38` positions each button with pixel offsets
(`"top": (this.ButtonHeight + this.Margin) * i`), i.e. the buttons are laid out in fixed offsets, not as
a ratio of the window size. I could not reconcile those numbers with the known-good 1280x720 coordinate
(491,553), so I do not claim a corrected position — I only report that the ratio scaling is wrong.

Other signals I tried and discarded (**observed**):
- The `404` that appears ~0.3 s after the first click is `http://127.0.0.1:8103/favicon.ico`
  (`performance.getEntriesByType('resource')` with `responseStatus >= 400`), i.e. Chrome refetching the
  favicon on first input — it appears after *every* first click, including the successful 1280x720 one,
  so it carries no information about page transitions.
- `Module.remoteStats` did not change across the clicks in either case
  (`reads 394, requests 33, bytes 23884978` before and after), so opening a page does not fetch new
  remote files that I could use as a marker.
- The canvas CSS cursor is a custom `data:image/png` cursor at every probed point
  (614,691 / 491,553 / 10,10), so hover state is not observable either.
