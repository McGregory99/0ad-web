# T0.2-E2 report — link wasi SpiderMonkey with Emscripten

STATUS: done

Experiment question: can Emscripten (emcc) link the wasi-sdk–built SpiderMonkey
libraries from T0.2-E1, and does JavaScript run in Node?

**Bottom line (observed):** No. Both link attempts fail. Without `-pthread` the linker
reports undefined symbols (first blocker: `gMozCrashReason`, a data symbol that no library
defines). With `-pthread` it additionally refuses the objects: `--shared-memory is disallowed
by Unified_cpp_js_src0.o because it was not compiled with 'atomics' or 'bulk-memory' features`.
No `js_hello.js` / `js_hello.wasm` was produced, so the Node run (Step 3) could not happen.

**Contents of `missing-symbols.txt` (observed, first 100 — file has 1 line):**
```
undefined symbol: gMozCrashReason
```

**Why only one symbol (observed + inferred):**
- **Observed:** even with `-sERROR_ON_UNDEFINED_SYMBOLS=0`, `wasm-ld` still errors out. The log
  contains 20 `undefined symbol: gMozCrashReason` error lines followed by
  `wasm-ld: error: too many errors emitted, stopping now (use -error-limit=0 to see all errors)`.
- **Observed:** `gMozCrashReason` is undefined in `libjs_static.a` (`llvm-nm --undefined-only`
  shows `         U gMozCrashReason`) and is **not defined** in `libjs_static.a` or
  `libjsrust.a` (`llvm-nm --defined-only` on both archives returns nothing for it).
- **Inferred:** `-sERROR_ON_UNDEFINED_SYMBOLS=0` only downgrades *function* imports; `wasm-ld`
  cannot import an undefined **data** symbol, so a missing global like `gMozCrashReason` is
  always a hard error. Because the same symbol repeats 20+ times, the 20-error cap is consumed
  before any other missing symbol is printed.
- **Derived:** therefore `missing-symbols.txt` (1 entry) **understates** the real missing set.
  The Step 1 histogram already showed at least 6 distinct symbols, and Step 4 shows the
  `-pthread` variant has additional, different failures. A complete list would require
  `-Wl,--error-limit=0` (or `-sERROR_ON_UNDEFINED_SYMBOLS=0` plus that flag); I did not add
  that flag because the runbook forbids inventing extra steps.

## Findings for the supervisor

1. **Two independent blockers, both observed.**
   - **Undefined data symbols / missing mozglue pieces:** `gMozCrashReason`, `moz_arena_malloc`,
     `moz_arena_realloc`, `mozilla::SIMD::memchr64(...)`, `mozilla::detail::MutexImpl::lock()/unlock()`.
     `gMozCrashReason` is `U` in `libjs_static.a` and defined in neither archive (observed with
     `llvm-nm`). These are mozglue/`memory/build` symbols; the E1 build's `--disable-jemalloc`
     plus the wasi target appear to have left them unprovided. **Inferred:** linking a small
     stub TU (or the mozglue static lib from the same objdir) that defines `gMozCrashReason` and
     the arena/mutex functions would clear this class of error.
   - **Thread/atomics mismatch:** wasi objects were compiled without `atomics`/`bulk-memory`,
     so any `-pthread` Emscripten link is refused (observed). This is a build-flag mismatch, not
     a symbol problem.

2. **The Step 2 recipe does not actually enumerate all missing symbols** (observed + derived):
   the 20-error cap is exhausted by repeated `gMozCrashReason` data-symbol errors, so
   `missing-symbols.txt` contains 1 line. A `-Wl,--error-limit=0` variant of the Step 2 command
   would be needed to get the true list — worth adding to the runbook.

3. **A cleaner strategy may be to build SpiderMonkey with emcc directly** rather than
   cross-linking wasi objects (inferred): Emscripten's libc (`dlmalloc`, no threads by default)
   differs from wasi-libc, so wasi-compiled objects bring both symbol gaps and ABI/feature
   mismatches. The `-pthread` result suggests threads must be decided at SpiderMonkey compile
   time, not at link time.
