What is written, and when — **observed**:

- **Logs, at every boot (InitVfs, before anything else):** `GameSetup.cpp:205-207` creates the logs

  `interestinglog.html`, `system_info.txt`, `userreport_hwdetect.txt` being written (see Step 3).
- **Config, when the user changes a setting:** `ps/GameSetup/Config.cpp:116` registers
  `config/user.cfg` as the `CFG_USER` namespace; writes go through
  `ps/ConfigDB.cpp:476,481,484,539` (`CConfigDB::WriteFile`), called from

- **Match settings, when the GUI saves them:** `ps/scripting/JSInterface_VFS.cpp:67` lists
  `config/matchsettings.json`, `config/matchsettings.mp.json` and `saves/campaigns/` as the paths the
  JS layer may write.
- **Replays, when a game starts:** `ps/Game.cpp:98` creates `m_ReplayLogger`;
  `ps/Game.cpp:407-410` `StartGame()` calls `m_ReplayLogger->StartGame(attribs)`;
  `ps/Replay.cpp:91` opens `m_Directory/"commands.txt"` with truncation and writes the `start` line

  `ps/Replay.cpp:140` logs `FILES| Replay metadata written to '…'`.
  Directory: `ps/VisualReplay.cpp:64` → `Paths(...).UserData() / "replays" / PS_SERIALIZATION_VERSION`
  (i.e. `…/replays/0.28.0`), one dated subdirectory per game. The replay **cache** is
  `VisualReplay.cpp:69` → `replayCache.json` and `VisualReplay.cpp:74` → `replayCache_temp.json`

- **Savegames, on explicit save:** `ps/SavedGame.cpp:67,84` build `saves/<name>` basenames and
  `:235,333` use `saves/<name>` for save/load; `:153` adds a `metadata.json` entry inside the

- **Screenshots:** `ps/GameSetup/GameSetup.cpp:226` mounts `screenshots/` writable;

- **Cache, opportunistically:** `GameSetup.cpp:222` mounts `cache/` as `VFS_MOUNT_ARCHIVABLE`, so XMB

## Summary: the folders that must survive a reload (observed/inferred)

**Observed** — the four writable locations the engine uses in the browser build:

| Path (browser) | Contents | Survives a reload today? |
|---|---|---|
| `/home/web_user/.local/share/0ad` | `saves/*.0adsave`, `replays/0.28.0/<date>/commands.txt` + `metadata.json` + `replayCache*.json`, `screenshots/`, user mod (`…/0ad/user/`) | **No** — plain MEMFS unless mounted |
| `/home/web_user/.config/0ad/config` | `user.cfg`, `console.txt`, `matchsettings.json`, `matchsettings.mp.json` | **No** |
| `/home/web_user/.cache/0ad` | XMB/VFS cache (`VFS_MOUNT_ARCHIVABLE`) | **No** (regenerable) |
| `/home/web_user/.local/state/0ad/log` | `mainlog.html`, `interestinglog.html`, `system_info.txt`, `userreport_hwdetect.txt` | **No** (diagnostics only) |

- **Inferred:** to make settings and saved games survive a page reload, the two directories that must
  be persisted are `.local/share/0ad` (savegames, replays, screenshots, user mod) and
  `.config/0ad/config` (settings). `.cache/0ad` and `.local/state/0ad/log` are safe to lose —
  the cache is rebuilt from the data archives and the logs are diagnostics.
- **Inferred:** the cheapest implementation is IDBFS: `FS.mkdirTree` + `FS.mount(IDBFS, {}, <dir>)`
  for those paths at `preRun`, `FS.syncfs(true, …)` once after mount to populate, and
  `FS.syncfs(false, …)` after the writes that matter (config save, game save, replay end). OPFS
  (`libwasmfs_opfs.js`) is the alternative with better performance but requires the WasmFS backend.
- **Not verified by this runbook:** whether the current web link already includes IDBFS/OPFS or
  `-sFORCE_FILESYSTEM`; I only inspected the SDK sources and the runtime logs. Checking the linker
  flags in `tools/wasm/build-engine.sh` would settle it (**inferred** that they are not yet used,
  because every run starts from an empty `/home/web_user` and writes appear only in MEMFS).
