# Runbook T7.1e — Room code: host shows it, joiner types it (worker t71e)

Read `runbooks/_wave7-common.md` first. Report: `reports/T7.1e.md`. Logs: `runs/T7.1e/`.
Starts after T7.1x is merged (it uses `failed` sockets from `reports/T7.1x.md`).

## Background (supervisor)

In the browser every ENet socket goes through the relay (`tools/relay/PROTOCOL.md`). A browser
host's UDP port on the relay is the port typed in the host dialog (default 20595). Players who
load the page from the same site share the relay, so a browser joiner reaches that host at
`127.0.0.1:<port>`. So the **room code is the relay port**, shown as digits. Native players
use `<relay hostname>:<port>`.

How GUI files reach the browser build: `tools/wasm/web/overlay/public/...` is preloaded over the
`public` mod (`tools/wasm/build-engine.sh:66`); a loose file there replaces the zip copy, and a
NEW `.js` file in a GUI folder that has `<script directory="...">` is loaded automatically after
the existing files of that folder (sorted by name), so it can redefine global functions.
The original GUI files are inside `data/mods/public/public.zip`
(`gui/gamesetup_mp/gamesetup_mp.js`, `.xml`). Extract single files to read them:
`D=$(mktemp -d); unzip -o -q data/mods/public/public.zip 'gui/gamesetup_mp/*' -d "$D"; echo $D`
(never extract into the repo).

Danger to fix first: if the requested port is taken on the relay, the host's own client still
connects to `127.0.0.1:<port>` (`upstream/source/network/scripting/JSInterface_Network.cpp:137`)
— that is somebody else's game. So the host must learn at once that the bind failed.

## Step 1 — enet_socket_bind waits for the relay's answer
In `enet-tunnel.c`, `enet_socket_bind`: after posting `TUNNEL_BIND`, when `port != 0`, wait
until the socket is `boundKnown` or `failed` (T7.1x), at most 5 seconds, using the existing
`tunnelLock` / `tunnelArrived` pair with `pthread_cond_timedwait` in a loop (absolute deadline
from `clock_gettime (CLOCK_REALTIME, ...)`). Return `-1` if it failed or timed out, else `0`.
This wait is allowed on the main thread (the WebSocket lives on the network I/O thread, which
answers without the main thread); write a comment saying so and why it is short (one relay
round trip, only when hosting). Check `zeroad_net_bound` broadcasts `tunnelArrived`; if it does
not, add `pthread_cond_broadcast (& tunnelArrived);` after its unlock. Port 0 (clients) keeps
returning 0 at once.

## Step 2 — Tell the GUI where the relay is
In `enet-tunnel.pre.js`, where `relayUrl` is computed (top of the file), on the main thread
only (`typeof window !== 'undefined'`), append the engine argument
`-conf=webnet.relay:<relayUrl>` to `Module.arguments` (create the array if missing; look at
`tools/wasm/web-env.pre.js` to see how arguments are set and do it the same way, after them).
The GUI reads it with `Engine.ConfigDB_GetValue("user", "webnet.relay")`.

## Step 3 — Room code logic (pure functions first, with tests)
Create `web_roomcode.js` with, at the top, pure functions that do not use `Engine`:
- `webRoomCodeParse(text)` → `{ host, port }` or `null`:
  `"20647"` → `{host:"127.0.0.1", port:20647}`; `" 20647 "` same (trim);
  `"relay.example.org:20647"` → that host and port; `"1.2.3.4:20700"` likewise;
  port must be an integer 1024..65535, otherwise `null`; `""`, `"abc"`, `"20647x"`,
  `"host:"`, `"host:99999"` → `null`.
- `webRoomCodeRandomPort(random)` → integer in 20700..20999 inclusive, `random` is a function
  returning [0,1) (pass `Math.random` in the game).
- `webRelayHostname(relayUrl)` → hostname part of a `ws://` / `wss://` URL
  (`"wss://play.example.org:20600/"` → `"play.example.org"`), `""` if it cannot parse.
Then create `tools/wasm/web/roomcode.test.mjs` that loads the file with `node:vm`
(`vm.runInNewContext(source, context)`), and tests every example above with `node:test` and
`node:assert`. Run:
`node --test tools/wasm/web/roomcode.test.mjs > runs/T7.1e/unit.log 2>&1; echo EXIT=$?; tail -15 runs/T7.1e/unit.log`
→ EXIT=0.

## Step 4 — Override the dialog (only when webnet.relay is set)
Read the original `gamesetup_mp.js` (extracted copy) to find `confirmSetup`, `startHost`,
`startJoin`, the init function and how the `joinServer`, `joinPort`, `hostPort` fields are
used. In `web_roomcode.js`, below the pure functions, when
`Engine.ConfigDB_GetValue("user", "webnet.relay")` is non-empty:
- Host page: on init, put `webRoomCodeRandomPort(Math.random)` into the `hostPort` field
  (do not save it to the config).
- Join page: the `joinServer` field accepts a room code or `host:port`. Wrap the original
  `confirmSetup` (keep a reference to it: `const webOriginalConfirmSetup = confirmSetup;`
  then reassign `confirmSetup`): if the join page is active and `webRoomCodeParse` of the
  `joinServer` caption is non-null, call the original `startJoin(name, host, port)` the same
  way the original code does, otherwise fall back to the original `confirmSetup`.
- After a successful host start, show the code: put
  `Room code: <port>   (native 0 A.D.: <relay hostname>:<port>)` into the `hostFeedback`
  caption, and `warn()` the same text so it is in the page console. If the original code does
  not give a hook after host start, wrap `startHost` the same way and do it after the original
  returns true.
- When hosting fails (`Engine.StartNetworkHost` throws), the original shows an error; keep that.
If `webnet.relay` is empty (native build), the file must change nothing. Keep the code short
and commented. Do NOT copy the whole original file.
