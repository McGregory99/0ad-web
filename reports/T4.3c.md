**observed** — `grep -nE 'remoteStats|Range|fetch\(|chunk|CHUNK|block|BLOCK|caches|persistent' tools/wasm/web-lib.js | head -60`
(plus reading the file around those lines) and `upstream/source/lib/file/archive/archive_zip.cpp`:

- **Fetch unit**: `blockSize: 256 << 10` = **256 KiB** aligned blocks. Each block is a separate
  in-memory LRU entry (`cacheLimit: 768 << 20` = 768 MiB) and a separate Cache Storage entry
  (`zeroad-blocks-v1`, key `${url}?size=…&block=N&bs=262144`).
- **Does a read of N bytes fetch more?** Yes. `zeroad_remote_pread` maps `[offset, offset+count)`
  to block indices `first = floor(offset/256KiB)` … `last = floor((offset+count-1)/256KiB)`; on a
  miss `load()` groups the missing blocks into contiguous spans and issues **one Range request per
  span**: `Range: bytes=${first*256KiB}-${(last+1)*256KiB-1}`, clamped to `remote.size-1`, and the
  response must be HTTP 206 with exactly that length. So every read rounds up to whole 256 KiB
  blocks. **derived** from the measurement: 724 of the 725 paths that fetched anything have
  `bytesFetched` an exact multiple of 262,144.
- **How a zip member is located**: not by URL — the engine reads the archive's index itself.
  `ArchiveReader_Zip` (archive_zip.cpp:466) scans the **last 66,000 bytes** for the ECDR
  (`ScanForEcdr`, `maxScanSize = 66000`), then reads the **whole central directory in one
  `io::Operation`** at `cd_ofs` and walks the CDFH records, creating
  `ArchiveFile_Zip(m_file, cdfh->HeaderOffset(), cdfh->CSize(), cdfh->Checksum(), cdfh->Method())`
  per entry; member data is then read by **absolute offset inside the archive**. There is only one
  remote URL (`remote-files.json` lists just `mods/public/public.zip`), so per-member attribution
  requires mapping offsets through that central directory.

## Three biggest savings you see (inferred)

1. **Smaller fetch granularity — up to ~100.9 MB (22.4% of the match download).**
   Numbers behind it (**observed/derived**): sum bytesRead 350.00 MB vs sum bytesFetched 450.92 MB;
   every `bytesFetched` value is a multiple of 262,144 (724/725 paths); `art/actors` fetched
   11,272,192 B for 384,137 B read (29×), `gui` 3,407,872 B for 1,618,574 B, `art/terrains`
   786,432 B for 331,622 B, and `gui/common/campaigns/CampaignRun.js` fetched 524,288 B for 7,258 B
   read. Dropping `blockSize` to 32–64 KiB (or fetching the exact byte range for small members)
   would recover most of that 100.9 MB without touching any asset.
2. **Textures are 240.4 MB of the 450.9 MB fetched (53%), and 224.9 MB of that is pre-converted
   `*.png.cached.dds` (407 files).** Numbers: `.dds` 240,386,048 B fetched / 196,613,458 B read;
   the top entries are single terrain/skin DDS files at ~2.8–5.6 MB each. Shipping compressed GPU
   formats (BC1/BC3 or KTX2) or a lower resolution tier for the first match would cut the largest
   single block of the download.
3. **Derived/cached assets are 94.7% of the traffic — 427.3 MB of 450.9 MB in 4,379 `.cached.`
   paths** (`.xml.cached.xmb` 125.0 MB, `.pmd` 32.5 MB, `.psa` 29.4 MB). Numbers: `.pmd` fetched
   32,505,856 B for only 11,272,500 B read (2.9×), `.psa` 29,360,128 B for 16,162,558 B. Serving
   the map's cached XML/mesh/animation set as a per-match bundle (or generating the `.xmb` on the
   client from the much smaller source `.xml`) avoids downloading caches for content the match
   never touches.
