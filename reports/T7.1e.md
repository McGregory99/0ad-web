## Bind wait (C change, what happens on failure/timeout)

**Observed** — `tools/wasm/enet-tunnel.c`, `enet_socket_bind`:

- New constant `#define TUNNEL_BIND_TIMEOUT_MS 5000` next to `TUNNEL_SEND`/`TUNNEL_RECV`.
- After `tunnel_post_control (TUNNEL_BIND, socket, generation, port)`:
  - `port == 0` returns `0` at once (clients; the relay picks the port and nobody needs it).
  - Otherwise it takes `tunnelLock`, re-looks-up the slot (and returns `-1` if the slot is gone or
    its generation changed), then loops
    `while (s->used && s->generation == generation && !s->boundKnown && !s->failed)`
    on `pthread_cond_timedwait (& tunnelArrived, & tunnelLock, & deadline)` with an absolute
    `CLOCK_REALTIME` deadline from the existing `tunnel_deadline()` helper (5 s). `ETIMEDOUT` breaks
    the loop.
  - Returns `0` only when `used && generation matches && boundKnown && !failed`; `-1` on timeout,
    on `failed` (relay ERROR or relay-side close, T7.1x), or on a dead slot.
- `zeroad_net_bound` did **not** broadcast `tunnelArrived` before (**observed** in the T7.1x code:
  it only set `boundKnown` under the lock); the runbook's conditional line was added:
  `pthread_cond_broadcast (& tunnelArrived);` after its unlock.
- Comment added in the code explaining why the wait is allowed on the main thread (the WebSocket
  lives on the network I/O thread, which answers without the main thread) and why it is short
  (one relay round trip, only when hosting).

**Failure path (derived from the engine source, not exercised here):** a failing bind makes
`enet_host_create` return NULL (`enet_host_create` destroys the socket and returns NULL when
`enet_socket_bind` fails) → `CNetServerWorker::SetupConnection` logs
`Net server: enet_host_create failed` and returns false (`upstream/source/network/NetServer.cpp:195,198`)
→ `StartNetworkHost` throws `std::runtime_error{"Failed to start server"}`
(`upstream/source/network/scripting/JSInterface_Network.cpp:92`) → the original `startHost` catch
shows the "Cannot host game: …" message box. So the host's own client, which connects to
`127.0.0.1:<port>` (`JSInterface_Network.cpp:137`), is never created against somebody else's game.

**Deviation from the runbook text (one line, deliberate):** after `if (port == 0) return 0;` the
code also has `if (! tunnelEnabled) return 0;`. In the Node profile there is no network I/O thread
(`Module.zeroadNet` is undefined, `enet-tunnel.c` starts no thread), so a `TUNNEL_BIND` is dropped
and no BOUND/ERROR can ever arrive: waiting 5 s there would turn the old "bind always succeeds"
into a 5 s stall plus `-1` for every Node host. The guard keeps the Node behaviour unchanged.
No Node test hosts, so this is defensive only.

**Observed in the smoke test:** the host's bind answer arrives normally and early —
`runs/T7.1e/mp/host.console.log`:
```

[19.8] log: [zeroad-net] socket 1: bound 0.0.0.0:54766 (requested port 0) (relay ws://127.0.0.1:20640/)
```

The match started at 42.1 s, i.e. well after the `bound` line, so the wait did not delay the match

## web_roomcode.js (functions, overrides, hooks used in the original file with line numbers)

New file `tools/wasm/web/overlay/public/gui/gamesetup_mp/web_roomcode.js` (4413 bytes, tabs, Allman
braces like the original). It is picked up because `gui/gamesetup_mp/gamesetup_mp.xml:6` has
`<script directory="gui/gamesetup_mp/"/>` and `CGUI::Xeromyces_ReadScript` loads every `*.js` of that
directory in sorted order (`upstream/source/gui/CGUI.cpp:1019-1036`), so `web_roomcode.js` runs after
`gamesetup_mp.js` and can reassign its globals (`std::map` iteration: "gamesetup_mp.js" <
"web_roomcode.js", **derived** from `vfs.cpp:107-123` + `vfs_tree.cpp:129`). The overlay is
preloaded over the public mod (`tools/wasm/build-engine.sh:66`); `web_roomcode.js` does not exist
in `public.zip`, so it is simply added next to the zip's files (**observed**:
`grep -c web_roomcode runs/web-t71e/pyrogenesis.js` = 1, and the preload metadata in that file
lists `gui/gamesetup_mp/web_roomcode.js`).

Pure functions (no `Engine`, tested):
- `webRoomCodeParse(text)` → `{ host, port }` / `null`: trims; a bare value must be all digits and
  a port in 1024..65535 with host `127.0.0.1`; `host:port` keeps the host (trimmed) and rejects an
  empty host, an empty port, a second colon, non-digits, and ports out of range.
- `webRoomCodeRandomPort(random)` → `20700 + floor(random()*300)`, clamped to 20700..20999.
- `webRelayHostname(relayUrl)` → `/^wss?:\/\/([^\/:?#]+)/i` match, else `""`. No `URL` object: the
  GUI script interface has none.

Overrides (inside `(function webRoomCodeInstall(){…})()`, which returns immediately when
`typeof Engine === "undefined"` — Node/tests — or when `Engine.ConfigDB_GetValue("user",
"webnet.relay")` is empty — native build; so a native build changes nothing):
- `init` (original `gamesetup_mp.js:70`): keeps `webOriginalInit`, and when
  `attribs.multiplayerGameType === "host"` sets `hostPort` to `webRoomCodeRandomPort(Math.random)`
  before calling it. Only the caption is set, never `ConfigDB_*` (**derived**: the XML Load action
  and `startHost` keep their own config handling). Note **observed** in the original: `startHost`
  still saves `multiplayerhosting.port` (line 421) — the random port therefore lands in the user
  config after a successful host; the next host init overwrites the field anyway, so this is
  harmless, and removing it would mean copying more of the original.
- `confirmSetup` (original `gamesetup_mp.js:150`): keeps `webOriginalConfirmSetup`; when `pageJoin`
  is visible and `webRoomCodeParse(joinServer.caption)` is non-null it does what the original join
  branch (lines 152-164) does — `startJoin(joinPlayerName, room.host, room.port)`, then
  `switchSetupPage("pageConnecting")` and `return false`, `return true` on failure — otherwise it
  falls back to the original (which uses `joinServer` + `getValidPort(joinPort)`, lines 155-158).
- `startHost` (original `gamesetup_mp.js:417`): keeps `webOriginalStartHost`; after it returns true,
  writes `Room code: <port>   (native 0 A.D.: <relay hostname>:<port>)` into `hostFeedback` and
  `warn()`s the same text. On failure/timeout it returns false before that, so the original
  message box for a thrown `Engine.StartNetworkHost` is the only feedback (unchanged).
