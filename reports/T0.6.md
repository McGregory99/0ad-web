## Where the remote time goes

Worker stats come from `ZEROAD_AI_WORKER_STATS` (`runs/T0.6-remote-2.worker.tsv`). Each line holds
the request type, ms, callbacks, callback ms, cached reads and request bytes. **Observed** sums:

| Request | n | worker ms | callbacks | callback ms | cached reads |
| --- | --- | --- | --- | --- | --- |
| compute | 12420 | 34006 | 1068810 | 23046 | 1583948 |
| gamestateInit | 1 | 378 | 3044 | 238 | 7271 |
| loadShared | 1 | 26 | 334 | 18 | 0 |
| addPlayer | 2 | 13 | 44 | 4 | 0 |
| init / templates | 1 / 1 | 2 / 2 | 20 / 0 | 0 / 0 | 0 |

- **Observed:** worker compute has p50 0.374 ms, p99 35.0 ms and max 378.9 ms. Requests total
  386.3 MB, which is the encoded game state sent every turn.
- **Observed:** 68% of the worker compute time (23.0 s of 34.0 s) is spent waiting for synchronous
  sim callbacks: 1.07 M RPCs, about 21.6 µs each including engine-side servicing. The per-turn read
  cache answered a further 1.58 M reads without a round trip.
- **Inferred:** the next optimizations, in order of size, are:
  - batching or caching more of the read-only sim queries (`Engine.*` and the `QueryInterface`
    proxy);
  - sending a state delta instead of the full state each turn.

  Neither is needed for correctness.

## Divergence found and fixed

- **Observed (before the fix):** the first divergence was at turn 27. A ptol house was placed at
  x 528.5, z 81.5 in-process but at x 536.5, z 88.5 remote, with the same RNG state. Two traces
  ruled out other causes:
  - The math trace (`ZEROAD_AI_TRACE_MATH`, `tools/bench/mathcmp.mjs`) first differs only at
    computation 45, so Math was not the cause.
  - The state trace (`ZEROAD_AI_TRACE_STATE`, `tools/bench/statecmp.mjs`) shows identical input
    state, passability and territory hashes through computation 27.
- **Observed (after the fix):** a 75 s smoke test matched for 8645 turns, and the full run matched
  all 12420.
- **Observed (root cause):** a scratch copy of `sm-sort.js` compared the SpiderMonkey result of each
  comparator sort with V8's native result. Only one call site differs:

  ```
  DIFF n=3 cmp=(a, b) => phaseList.indexOf(a) - phaseList.indexOf(phaseMap[b])
    at UnravelPhases (globalscripts/Technologies.js:393:12) | at GameState.init (simulation/ai/common-api/gamestate.js:63:16)
  ```

  The comparator is inconsistent because it maps only `b` through `phaseMap`. Its result therefore
  depends on the sort algorithm: SpiderMonkey 128 uses insertion sort for ≤ 8 elements, and V8
  uses a binary insertion sort / TimSort. The resulting phase order feeds Petra's build decisions.
- **Fix:** `tools/wasm/ai/sm-sort.js` replaces `Array.prototype.sort` and
  `%TypedArray%.prototype.sort` in the worker, only for calls with a comparator. It is a port of
  `ArraySortData::sortWithComparatorShared` from mozjs-128.13.0 (`js/src/builtin/Sorting-inl.h`
  and `Array.cpp`):
  - insertion sort for ≤ 8 elements;
  - otherwise, 4-element insertion windows and then a bottom-up merge that skips ordered pairs;
  - NaN counts as "less or equal";
  - undefined values sort last, and holes are moved to the end.

  Without a comparator the native sort is kept, because both engines define that order.

## Design (as built)

- **Opt-in:** `ZEROAD_AI_REMOTE=1` (default off), only in `__EMSCRIPTEN__` builds (`AI_REMOTE`).
  The in-process path is unchanged apart from the env-gated log and trace hooks.
- **Native timing is kept:** `CCmpAIManager::StartComputation` / `PushCommands` still run the AI
  synchronously at the end of the turn. In remote mode `PerformComputation` sends `{type:'compute',
  state, hasShared}` and any dirty grids, then blocks until the worker replies with
  `{commands, rng}`.
- **Transport:**
  - `zeroad_ai_remote_call` (`tools/wasm/node-lib.js`) writes the request into a growable
    SharedArrayBuffer, notifies the worker and waits with `Atomics.wait` on the engine thread.
  - The worker answers either with the final reply (kind 0) or with a callback request. The engine
    services callbacks re-entrantly through the wasm exports `zeroad_ai_service_*`
    (`AIRemote.cpp`).
  - Callbacks include sim reads and calls, `QueryInterface`, AI module code, global scripts and
    logs.
- **Worker** (`tools/wasm/ai/ai-worker.js`):
  - mirrors `CAIWorker` (init, templates, addPlayer, loadShared, gamestateInit, compute);
  - loads AI ES modules from the engine VFS through `module.registerHooks` with the `zeroad-vfs:`
    scheme;
  - replicates boost `rand48` bit-exactly, with the state passed on every request and reply;
  - keeps the SpiderMonkey property order (`Script::CreateObject` sets properties in reverse) and
    the read-only map properties;
  - deep-freezes templates.
- **Codec:** `tools/wasm/ai/codec.js` has a byte-identical copy embedded in `CCmpAIManager.cpp`.
  `codec.test.mjs` checks that the two stay in sync. The codec handles Set, Map, typed arrays and
  -0, using cross-realm brand checks.
- **Oracle:** `ZEROAD_AI_LOG=<file>` writes `T <turn> <count> <rng>` and `C <player> <json>` lines in
  `PushCommands` (both modes). `ZEROAD_AI_HASH_SKIP_SCRIPTS=1` excludes the AI script objects from
  the state hash, and remote mode forces this. The comparison script is `tools/bench/aicmp.mjs`.

## Browser path (design, not implemented)

`tools/wasm/web-lib.js` stubs `zeroad_ai_remote_call` to return -1. The engine then logs an error
and keeps going without remote commands, so `ZEROAD_AI_REMOTE` must stay off in the web profile.
The planned design:

1. **Worker:** a dedicated Web Worker (`ai-worker.js` browser branch) receives `{ctrl, data,
   memory}` via `postMessage`. The worker can still block with `Atomics.wait`, so its side of the
   protocol does not change.
2. **Engine side:** the browser main thread cannot call `Atomics.wait`. Make
   `zeroad_ai_remote_call` an async JSPI import (`__async: true`; the web build already uses
   `-sJSPI=1`).
   - It awaits `Atomics.waitAsync(ctrl, 0, 1).value` in a loop.
   - While suspended it services callbacks by calling the `zeroad_ai_service_*` exports. Those are
     synchronous exports that do not suspend.
   - This keeps native timing: the sim turn is suspended rather than split.
   - **Inferred risk:** re-entering wasm exports while a JSPI suspension is active must not touch
     state owned by the suspended frame. The service only reads sim state and uses its own buffers,
     but this needs a test.
   - **Inferred risk:** Node's `Atomics.waitAsync` in a worker missed wake-ups in this task (a
     standalone test stalled after 3 round trips). The browser path must be tested for this. A
     `MessageChannel` doorbell is the fallback.
3. **AI module loading:** ES `import` in a worker cannot use the sync VFS RPC. Options:
   - (a) a Service Worker answering `zeroad-vfs/` URLs from the streamed `public.zip`;
   - (b) prefetch the AI module graph once at init over RPC and rewrite the specifiers to `blob:`
     URLs.

   (b) is simpler and needs no new global state.
4. **Determinism:** the worker must still install `sm-sort.js` and the rand48 `Math.random`. V8
   and JavaScriptCore have different sort algorithms, so the SpiderMonkey sort also covers
   Safari.

## Open problems

- **Saved games:** savegames and serialization are not supported in remote mode. `Deserialize`
  raises an error, and `SerializeState` skips the AI script state. Rejoin and save need a
  worker-side serialize/deserialize that matches `CAIWorker`'s format.
- **No sandbox:** the Node worker runs AI scripts with Node privileges. In the browser the Web
  Worker is the sandbox.
- **Object identity:** sim objects returned by reference in-process (for example
  `GetResourceCounts`, `GetResearchedTechs`) are copies or proxies remotely. Aliasing-dependent AI
  code would differ. None was observed in this replay.
- **Engine semantics:** other engine-specific behaviours, such as `Math` precision and property
  enumeration edge cases, matched on this replay only. Other maps and civs may hit new cases. The
  math and state traces are kept for diagnosing them.
- **Patch size:** `patches/upstream/0019-emscripten-remote-ai.patch` (3 files, 1027 lines) includes
  the env-gated diagnostic traces in `CCmpAIManager.cpp`. They could be split out before
  upstreaming.
