# Runbook T0.4a — Where do the slow turns come from? (GC profile, native vs wasm)

Context: in the wasm replay most turns are fast (median 5 ms) but 56 turns take more than 200 ms
(max 1.1 s). The supervisor suspects SpiderMonkey garbage collection (GC). SpiderMonkey prints a
GC timing table to stderr when the env var `JS_GC_PROFILE` is set. You COLLECT logs; you do not
change engine code and you do not debug.

- Root: `~/DEVELOPMENT/0ad-web` (ROOT). Write only in `ROOT/runs/`, `ROOT/upstream/binaries/system-wasm/`
  (rebuilt by the script) and temporary HOME dirs from `mktemp -d`.
- Report: `ROOT/reports/T0.4a.md`. Do NOT touch `upstream/binaries/system-wasm-pbl/` (another worker uses it).
- If any step fails: paste the output in the report and STOP. Do not try fixes.

## Step 1 — Relink the wasm engine (the supervisor changed `tools/wasm/node-env.pre.js`)

```bash
cd ~/DEVELOPMENT/0ad-web
rm upstream/binaries/system-wasm/pyrogenesis upstream/binaries/system-wasm/pyrogenesis.wasm

ls -la upstream/binaries/system-wasm/
grep -c 'JS_GC_' upstream/binaries/system-wasm/pyrogenesis
```

Expected: `EXIT=0`, both files exist again, and the grep count is 1 or more.

## Step 2 — Native replay with GC profile (about 1 minute)

```bash
cd ~/DEVELOPMENT/0ad-web/upstream/binaries/system
R=~/DEVELOPMENT/0ad-web; H=$(mktemp -d); echo "TEMP HOME=$H"
HOME=$H JS_GC_PROFILE=0 JS_GC_PROFILE_NURSERY=1 perl -e 'alarm shift; exec @ARGV' 900 \
  ./pyrogenesis -replay="$R/fixtures/reference-replay/commands.txt" 2>&1 \
  | node $R/tools/bench/turnstats.mjs $R/runs/T0.4a-native-gc.tsv > $R/runs/T0.4a-native-gc.stats
cat $R/runs/T0.4a-native-gc.stats
grep -cE 'MajorGC|MinorGC' $R/runs/T0.4a-native-gc.tsv
grep -E 'MajorGC|MinorGC' $R/runs/T0.4a-native-gc.tsv | head -8
```
