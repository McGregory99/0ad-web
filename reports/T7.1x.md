STATUS: done

## Changes (file: what changed)

- **`tools/relay/relay.mjs`** (Step 2)
  - Added `let binding = false;` next to `let udp = null, ...`.
  - Message handler: after the `lastActive` update and the binary check, `if (binding) { stats.dropped++; return; }`.
  - BIND branch now creates the socket into a local `const socket`, sets `binding = true`, awaits
    `bindUdp(socket, wanted)` into `udpPort`, and only assigns `udp = socket` after the bind
    succeeded and `closed` is false. On bind error it closes that one socket, clears `binding`
    and returns `closed ? undefined : fail(...)`; if the WebSocket closed during the bind it closes
    the socket once and returns. The first-message check is still `if (!udp)`.
  - Result: no double `close()`, no `ERR_SOCKET_DGRAM_NOT_RUNNING`, the UDP socket is closed exactly
    once (by `close()` if it was assigned to `udp`, otherwise by the code after the `await`).

- **`tools/relay/relay.test.mjs`** (Step 1) — new test
  `'WebSocket closed during the UDP bind: no crash, relay keeps working'` (20 x BIND 0 + immediate
  `terminate()`, 500 ms wait, then a normal session must get BOUND, error array must be empty).
  Deviation from the runbook text: Node's global WebSocket has no `terminate()`
  (**observed**: `typeof w.terminate === 'undefined'`), so the test uses the relay's own `ws`
  package client (`tools/emsdk/upstream/emscripten/node_modules/ws/index.js`, loaded with
  `createRequire`) for the terminated connections only. The rest uses the file's existing helpers.

- **`tools/wasm/enet-tunnel.c`** (Step 3)
  - `TunnelSocket` gains `int failed;` right after `boundKnown`, with the runbook comment.
  - New exported `zeroad_net_failed(slot, generation)` next to `zeroad_net_bound`; it sets
    `s -> failed = 1` for a matching live slot under `tunnelLock` and broadcasts `tunnelArrived`.
  - Slot (re)initialisation: no extra line was needed — `enet_socket_create` already does
    `memset (s, 0, sizeof (* s))` before setting `used`/`generation`, so `failed` starts at 0 for
    every new socket (the same place that clears `boundKnown`).
  - `enet_socket_send`: reads `s = tunnel_get (socket)` under the lock and treats
    `valid = s != NULL && ! s -> failed`; a failed socket returns `-1`.
  - `enet_socket_receive`: captures `failed` under the lock; with no queued frame it returns
    `failed ? -1 : 0`, so frames that arrived before the failure are still delivered first.
  - `enet_socketset_select`: a failed socket counts as readable in the ready count and is kept in
    the read set.
  - `enet_socket_wait`: the blocking loop also stops when `s -> failed`, and a failed socket sets
    `ENET_SOCKET_WAIT_RECEIVE` so the caller's next receive returns `-1` immediately.

- **`tools/wasm/enet-tunnel.pre.js`** (Step 4)
  - `onMessage` ERROR branch: after the log line, `_zeroad_net_failed(s.slot, s.generation);`.
  - `s.ws.onclose`: inside the existing `if (!s.closed)` case (relay closed, not the engine) it now
    also calls `_zeroad_net_failed(s.slot, s.generation);`. The engine-close path (`CLOSE` command,
    which sets `s.closed` before `ws.close()`) does not call it.

- **`tools/relay/PROTOCOL.md`** (Step 4) — ERROR row gains: "The browser marks the socket failed:
  ENet's send and receive on it return -1."

The relay side agrees (`runs/T7.1x/mp-busy/relay.log`): `#1 ... closed (bind 20595: EADDRINUSE)`,
then `#2 ... bound udp 54560` (the host's client-side ENet host, requested port 0) and
`#3 ... bound udp 51902` (the joining browser client).

**Not observed:** `enet_host_service failed (-1)` is **not** in `host.mainlog.html`, because that
file does not exist. `ls runs/T7.1x/mp-busy` shows only
`client.console.log host.console.log mp-check.log relay.log`; the runbook's grep reports
`grep: runs/T7.1x/mp-busy/host.mainlog.html: No such file or directory`, and
`host.interestinglog.html` is missing too (same search: `ls runs/T7.1x/mp-busy/host.interestinglog.html`).

**Observed — why it is missing:** mp-check did reach the expected timeout
(`runs/T7.1x/mp-busy.log`, last line: `[64.6] timeout waiting for both pages in the match`), but
then hung. mp-check writes `{host,client}.{mainlog,interestinglog}.html` and the PNGs only after
`Page.captureScreenshot`; the host page's main thread is stuck (the engine's autostart wait), so
that CDP call never returns. The harness killed my shell at its 900 s limit, so the run never
reached the log-copy loop. The engine log lives in the page's IDBFS
(`/home/web_user/.local/state/0ad/log/mainlog.html`), not on disk, so it cannot be read after the
run. Per the runbook I did not change mp-check or other code.

**Derived:** the failed socket carried no traffic after the ERROR (socket 0 is closed by the relay
and never reopens; only the newly created client-side socket 1 is bound), so the failure did reach
the tunnel. Whether `NetServer.cpp` logged `enet_host_service failed (-1)` could not be checked
without the engine log — **inferred**, not observed.

## Open questions

1. The RED test passed on the first run, so the relay bind race is not proven by a failing test
   here; the fix follows the runbook code and all 10 tests stay green. A deterministic RED would
   need a hook that delays `bindUdp`'s `listening` event (not in scope).
2. `enet_host_service failed (-1)` is unverified because mp-check hangs on the stuck host page
   before it copies `mainlog.html`. To see it, mp-check would need a screenshot/log-collection path
   that tolerates an unresponsive page (out of scope: "do not change other code").
3. Harness note (**observed**): the first two Step 7 attempts were killed by the harness time
   limit, and the killed `with-lock.sh` shell left a stale `runs/.mp.lock` (owner pid dead, trap not
   run on SIGKILL). I removed the stale lock only after `ps -p <pid>` confirmed the owner was dead;
   this also unblocked worker t71c, which was waiting on the same lock. No process was left holding
   UDP 20595 (`lsof -nP -iUDP:20595` empty after cleanup).
4. Host/client report `error lines 2` / `error lines 1` in the passing Step 6 run; I did not inspect
   them (they are pre-existing page error lines, not relay errors — relay stats show `errors: 0`).
