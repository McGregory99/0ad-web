# T7.1 — Multiplayer networking for the browser build: design report

Read-only research, 2026-11-16. Inputs: `odd/tasks/0ad-web.md` (S1, S7, S8, T7.1, T7.2), `upstream/source/network/*`, `wasm/deps/src/enet-1.3.18`, Emscripten 6.0.13 in `tools/emsdk/upstream/emscripten`. Nothing was built or run; claims marked *to verify* are design inferences that a runbook must prove.

## 1. Recommendation

**Keep ENet and every line of `NetSession`/`NetServer`. Replace only ENet's OS socket layer (`unix.c`, 13 `enet_socket_*` functions) with a WebSocket "datagram tunnel" to a small UDP relay.** The relay gives each browser ENet host a real UDP port, so:

- browser joins browser: both tunnels end on the relay, which forwards datagrams;
- browser joins native 0.28 host: relay sends the browser's datagrams as UDP to the native host;
- native 0.28 client joins browser host: native client connects by UDP to `relay-ip:allocated-port`.

ENet's own reliability runs on top unchanged; the game only uses one reliable channel, so a reliable (TCP-backed) tunnel costs nothing functionally.

Cheapest proof first: a spike with Emscripten's stock `-sPROXY_POSIX_SOCKETS` + `websocket_to_posix_proxy` (zero engine code) to prove the multiplayer stack runs in the browser on localhost. That proxy is an unrestricted socket proxy (any host, any port), so it must never be exposed publicly; the custom tunnel + relay replaces it for real use.

WebRTC (option B) is the better long-term *latency/cost* option for browser-to-browser, but it loses native interop, needs signalling + STUN + TURN, and is more code. It can later be added as a second backend behind the same ENet socket shim. Option C (replace ENet at `NetSession` level) is the most invasive and loses interop; not recommended.

Rough cost of the recommended path: ~350–500 lines C/JS in the engine build (new `enet` socket backend + JS glue + small `#ifdef __EMSCRIPTEN__` in STUN/UPnP paths), ~250–400 lines for the relay (Node or Go), plus hosting (needs the user's OK, T4.4). Localhost testing needs no hosting.

## 3. Options

| | A1. SOCKFS / PROXY_POSIX_SOCKETS | A2. Custom ENet socket layer + UDP relay (**recommended**) | B. WebRTC DataChannel | C. WebSocket at NetSession level |
|---|---|---|---|---|
| Engine change | link flags only | replace `unix.c` socket fns (~250 C) + JS glue (~150) + small `#ifdef` | ENet socket shim over DataChannel (~300 C/JS) + JS peer management (~300) | rewrite `CNetClientSession`/`CNetServerSession`/worker event loop (~600–900) |
| Browser can host? | SOCKFS: **no** (`listen` → `EOPNOTSUPP`). PROXY: yes (port lives on the proxy machine) | yes (relay allocates UDP port) | yes (no listening needed; host is a peer that accepts offers via signalling) | yes (relay routes) |
| Native 0.28 interop | SOCKFS: no (needs a WS↔UDP bridge per target; websockify is TCP-only). PROXY: yes | **yes, both directions** | no (would need a WebRTC↔UDP gateway) | no (relay would have to speak ENet) |
| Server side | PROXY: `websocket_to_posix_proxy` (native, unrestricted) | relay: WS endpoint + UDP port pool, session/room codes (~250–400 LOC) | signalling (~150 LOC) + STUN + TURN (coturn) | relay router (~300 LOC) |
| Transport semantics | TCP under ENet | TCP under ENet; ENet still acks/sequences (harmless, no loss so no retransmits) | true unreliable/unordered datagrams; ENet does reliability — the native-like setup | TCP; ENet removed |
| Latency | +1 relay hop | +1 relay hop (browser↔relay↔peer) | direct P2P when NAT allows; TURN hop otherwise | +1 relay hop |
| Threading | SOCKFS state is main-thread JS; net threads' `select`/`recvfrom` become sync proxies to main thread. | Security | PROXY is an open proxy: localhost only | relay only forwards to registered ENet peers / allocated ports; rate limits | TURN credentials, signalling auth | relay auth |
| Verdict | **spike only** | **ship** | later backend for P2P | no |

## 4. Touch points (recommended path)

1. `wasm/deps/src/enet-1.3.18/unix.c` — keep `enet_address_*` and `enet_time_*`; route `enet_socket_create/bind/send/receive/wait/destroy/get_address/set_option` for `ENET_SOCKET_TYPE_DATAGRAM` to the tunnel when `__EMSCRIPTEN__`. Best done as a separate `wasm/deps/patches/enet-websocket.c` compiled instead of `unix.c` by the deps build script, so upstream ENet stays pristine.
   - `bind(addr)`: ask relay for a UDP port (port 0 → any); `get_address` returns `relay-ip:port`.
   - `send(addr, buffers)`: frame `[ipv4][port][payload]` into one binary WS message.
   - `receive`: pop one frame from the ring buffer, fill `ENetAddress` from its header.
   - `wait(timeout)`: `emscripten_futex_wait` on the ring's write counter with the timeout (ENet polls with 50 ms).
2. JS glue (`--js-library`, e.g. `tools/wasm/enet-tunnel.js`): owns the `WebSocket` on the main thread, pushes received frames into the ring in shared wasm memory, drains the outbound ring. Relies on the JSPI main loop yielding to the event loop each frame (already true for rendering).
3. `upstream/source/network/NetClient.cpp:249-300`, `NetServer.cpp:1700,1750` — STUN/hole punching: compile out under `__EMSCRIPTEN__` (lobby path only; relay makes it unnecessary).
4. `NetServer.cpp:213` UPnP thread — already disabled by `--without-miniupnpc`; confirm no thread is spawned.
5. Host/join GUI: `network/scripting/JSInterface_Network.cpp:78` (`StartNetworkHost`), `:148` (`StartNetworkJoin`). Join takes `address:port` today; the relay address is what the browser host shows. Optional: a room code that the relay resolves to an allocated port (GUI text only, no engine change).
6. Link flags in `tools/wasm/build-engine.sh`: none for A2 beyond the JS library; `-sPROXY_POSIX_SOCKETS -lwebsocket.js` plus native build of the proxy for the A1 spike.

## 5. Server pieces

- **Relay** (`tools/relay/`, Node `ws` + `dgram`, or Go): WS endpoint (`wss://` in production, since the game is served over HTTPS); per WS session one UDP socket bound on the relay; forwards frames ↔ UDP. Browser↔browser goes through two relay sockets on the same host. Limits: per-session bandwidth cap (lockstep traffic is a few KB/s per player), idle timeout, port range (e.g. 20600–20700).
- **Hosting**: a VPS with public IPv4, open UDP port range and TLS. Needs the user's OK (T4.4). Bandwidth is small (all players' commands, not state). Localhost + LAN testing needs none.
- WebRTC later: signalling can live in the same relay process; TURN (coturn) is a separate service.

## 6. Risks

1. **Thread/event-loop coupling**: net threads must never wait on the main thread while the main thread waits on them (e.g. main thread blocked in a mutex the net thread holds while it waits for a sync proxy). The ring-buffer design avoids sync proxies on the hot path; SOCKFS/PROXY do not (*to verify in spike*).
2. **Main thread stalls** (loading, long sim turns) delay WS delivery; ENet timeouts (default ~5–30 s) are far above expected stalls, but `NETWORK_BAD_PING` warnings may show during map load.
3. **ENet MTU**: `NetEnet.cpp:51` sets 1372; the tunnel adds ~6 bytes on WS only, UDP side unchanged — fine.
4. **Native interop is version-locked**: 0.28 wasm and 0.28 native must share the same mods/data hash; the light data profile (S7: 1 map, 2 civs) will fail the setup hash check against a full native install unless matched. *Interop with native is limited by data, not transport.*
5. **Desync risk** is independent of transport (existing replay-hash tests cover sim determinism).
6. **Open-proxy exposure** if the A1 spike proxy is ever left reachable.

## 8. Lobby (T7.2)

The lobby is XMPP via gloox (`--without-lobby` today). Browsers can't open raw TCP to XMPP port 5222; it would need XMPP over WebSocket (RFC 7395), which gloox does not provide as a transport, and the official Wildfire Games lobby server would have to expose a WebSocket endpoint (not known; *to verify*) — and its STUN-based hosting flow does not apply to browsers. Options: (a) custom gloox `ConnectionBase` over the same WS glue (~300 LOC, lobby GUI unchanged), or (b) a minimal relay-side game list (host registers, joiners list rooms) with a small GUI page. **It can wait**: host/join by address or room code covers S1/S7; T7.2 is not needed for the first multiplayer milestone.
